# 0007: Denied requests return 404 for other users' resources

Status: Accepted

## Context

The most common real-world API bug in this class of system is an IDOR (Insecure Direct Object
Reference): a user changes an ID in the URL and reaches someone else's data because the server
checked *authentication* (are you logged in) but not *ownership* (is this actually yours).

`OwnershipSecurityIT` exists specifically to catch a regression here: it registers two users,
has one create a vehicle and a key, and asserts every endpoint returns 404 — never 403 — when
the other user tries to view, suspend, revoke, or list keys on it.

## Decision

`KeyAuthorization` and the equivalent ownership checks in `VehicleController`/`AuditController`
throw `NotFoundException` (mapped to HTTP 404) rather than a "forbidden" response when the
resource exists but doesn't belong to the caller.

## Consequences

A 403 response confirms a resource exists at that ID even if you can't touch it — which itself
leaks information (an attacker enumerating IDs can map out how many vehicles or keys exist and
roughly when they were created, from UUID ordering or simple ID-count timing). A 404 gives an
attacker nothing to distinguish "doesn't exist" from "exists, not yours."

The trade-off is a slightly less informative error for legitimate callers who make an honest
mistake (a typo'd VIN and a real-but-not-theirs VIN look identical). That's judged an acceptable
cost for the confidentiality this buys.

## Alternatives considered

- **403 Forbidden**: the more conventional REST response for "you can't do that," and arguably
  more helpful during development. Rejected specifically because "more helpful" here is
  synonymous with "more informative to an attacker."
